Bug-Fixing Prompt 模板

用于编译器调试与性能分析场景的结构化 Prompt 模板。复制模板，填入具体信息后发送给 AI 助手。

使用方式

  1. 点击代码块右上角的 Copy 按钮复制模板
  2. 将 {{占位符}} 替换为实际信息
  3. 发送给 AI 助手

模板

# Bug 修复请求

## 1. 症状描述

**错误类型**: {{编译错误 / 运行时错误 / 错误输出 / 性能退化}}
**错误信息**:
```
{{粘贴完整的错误信息或 diff 输出}}
```

**测试用例**: `/test/performance/{{name}}.sy`
**预期输入**: `/test/performance/{{name}}.in`
**预期输出**: `/test/performance/{{name}}.out`
**原性能**: {{粘贴 test/results/ 下对应的 .txt 结果，或留空}}

## 2. 复现步骤

```bash
# 查找正在运行的 Docker 容器
docker ps -a

# 进入容器（不要使用 qemu）
docker exec -it {{container_id}} /bin/bash

# 编译（调试选项参考 README.md）
cd /workspace && mkdir -p build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Debug && make -j$(nproc)

# 运行全量测试（测试输出已包含计时，无需单独计时）
cd /workspace/test
bash arm_functional.sh   # 功能测试
bash arm_performance.sh  # 性能测试（不要使用 final 版本）
```

## 3. 期望行为

- **正确性优先**：若改动仅影响 -O1 开启才会触发的优化，只需运行 `arm_performance.sh` 并保证全部通过
- **性能退化判断**：若出现性能退步，先确认是否符合预期行为（如 Pass 语义变更），再具体分析退化原因
- **计时波动**：Docker 容器环境不稳定，时间波动属正常现象，不必过度关注微小差异
- **目标架构**：Cortex-A53 CPU，本机无法模拟，需自行判断何种优化利好 A53（如短流水线、低延迟指令、减少分支预测失败等）

请提供：
1. **根因分析** — Bug 产生的根本原因
2. **最小修复方案** — 具体的代码修改（文件路径 + diff）
3. **影响评估** — 修复可能影响的其他测试

填写指南

第 1 节：症状描述

测试用例统一使用 /test/performance/{name}.sy 路径格式。预期输入/输出分别对应同目录下的 .in 和 .out 文件。原性能栏粘贴 test/results/ 下带时间戳的 .txt 文件内容，用于对比退化幅度。

第 2 节：复现步骤

始终使用已运行的 Docker 容器（docker exec），不要启动新容器或使用 qemu 模拟。编译器的调试选项（如 --dump-ir、--emit-ir 等）请参考项目 README.md。全量测试脚本位于 /test 目录，使用 arm_ 前缀的脚本（arm_functional.sh、arm_performance.sh），不要使用 final 后缀的版本。测试脚本输出中已包含每个用例的计时信息。

第 3 节：期望行为

Cortex-A53 是顺序执行的 ARMv8 核心，偏好短依赖链、低延迟指令和紧凑的代码体积。在分析性能影响时，应结合 A53 的流水线特征判断优化是否有效，而非仅依据本机 x86 测试结果。
