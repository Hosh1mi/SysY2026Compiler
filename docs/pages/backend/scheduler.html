指令调度

MachineScheduler 在寄存器分配之后、Peephole 优化之前运行，通过 segment-based list scheduling 重排基本块内的机器指令，利用指令级并行性（ILP）减少流水线停顿。

概览

调度器采用经典的 List Scheduling 算法，以基本块内的"segment"为单位进行局部调度：

  1. 按 barrier / label 将指令序列切分为多个 segment
  2. 对每个 segment 构建依赖图（DAG）
  3. 计算每条指令的关键路径长度作为优先级
  4. 按优先级从就绪队列中选取指令发射

类定义

// src/include/backend/arm64/scheduler.hpp
class MachineScheduler {
public:
    void schedule(MachineFunction &func);
private:
    struct Dep { int from; int to; };  // 依赖边
    void scheduleSegment(std::vector<MachineInstr*> &instrs);
};

Segment 分割

schedule() 遍历函数中所有基本块的指令，以 barrier 指令（branch、ret、bl）和 label 为界将指令序列切分为 segment：

void MachineScheduler::schedule(MachineFunction &func) {
    for (auto &bb : func.blocks) {
        // 收集所有指令
        std::vector<MachineInstr*> allInstrs;
        for (auto &instr : bb.instrs)
            allInstrs.push_back(instr.get());

        // 按 barrier/label 切分
        std::vector<MachineInstr*> segment;
        for (auto *instr : allInstrs) {
            if (instr->isBarrier() || instr->isLabel()) {
                if (!segment.empty()) {
                    scheduleSegment(segment);  // 调度当前段
                    result.insert(result.end(), segment.begin(), segment.end());
                    segment.clear();
                }
                result.push_back(instr);  // barrier/label 原样保留
            } else {
                segment.push_back(instr);
            }
        }
        // 处理最后一个 segment
    }
}

barrier 和 label 不参与调度，保证控制流的正确性。

依赖图构建

scheduleSegment 首先构建指令之间的依赖关系 DAG。三种依赖类型：

类型含义检测方式
RAW（Read After Write）j 读取 i 定义的值i.defs ∩ j.uses ≠ ∅
WAW（Write After Write）i 和 j 定义同一寄存器i.defs ∩ j.defs ≠ ∅
WAR（Write After Read）j 写入 i 读取的寄存器i.uses ∩ j.defs ≠ ∅

虚拟寄存器

为了正确处理隐式依赖，引入两个虚拟寄存器：

  • $flags — 条件标志寄存器。所有 cmp、tst 等设置标志的指令 def $flags；所有条件分支（b.cond、csel、ccmp）use $flags
  • $mem — 内存序虚拟寄存器。所有 mayLoad/mayStore 指令同时 def 和 use $mem，确保内存操作之间的全序关系
// 依赖图构建核心逻辑
for (int i = 0; i < n; i++) {
    for (int j = i + 1; j < n; j++) {
        auto &ai = instrs[i], &aj = instrs[j];
        // 检查 ai → aj 是否存在 RAW / WAW / WAR
        bool raw = hasIntersection(ai.defs, aj.uses);
        bool waw = hasIntersection(ai.defs, aj.defs);
        bool war = hasIntersection(ai.uses, aj.defs);
        if (raw || waw || war) {
            deps.push_back({i, j});  // i → j 有依赖
            adj[i].push_back(j);
        }
    }
}

关键路径优先级

从依赖图反向（从后往前）计算每条指令的 关键路径长度（Critical Path），作为调度优先级：

// 反向计算关键路径长度
// cp[i] = latency(i) + max{cp[j] | i → j ∈ deps}
std::vector<int> cp(n, 0);
for (int i = n - 1; i >= 0; i--) {
    cp[i] = latency(instrs[i]);  // 指令延迟
    for (int j : adj[i])
        cp[i] = std::max(cp[i], latency(instrs[i]) + cp[j]);
}

典型延迟值：

指令类型延迟
整数 ALU（add, sub, and, orr...）1
整数乘法（mul, madd）3
整数除法（sdiv, udiv）12
Load（ldr, ldp）4
浮点运算（fadd, fmul, fdiv）4 / 4 / 12
其他1

List Scheduling

调度算法维护一个 就绪队列（所有前驱已发射的指令），每步从中选取优先级最高的指令发射：

// List Scheduling 核心
std::vector<int> inDegree(n, 0);
// ... 计算入度 ...

auto ready = [&](int idx) { return inDegree[idx] == 0; };
std::vector<int> scheduled;

for (int step = 0; step < n; step++) {
    // 从就绪队列中选取优先级最高的指令
    int best = -1;
    for (int i = 0; i < n; i++) {
        if (!scheduled_set.count(i) && ready(i)) {
            if (best == -1 || compare(i, best, cp, instrs, scheduled))
                best = i;
        }
    }
    // 发射 best，更新后继入度
    scheduled.push_back(best);
    scheduled_set.insert(best);
    for (int j : adj[best]) {
        if (--inDegree[j] == 0) { /* j 进入就绪队列 */ }
    }
}

选取策略（优先级排序）

当多条指令同时就绪时，按以下优先级选取：

  1. Load-Use Hazard 避免 — 如果前一条指令是 load 且当前候选使用该 load 的结果，则降低优先级（延迟 4 个周期）
  2. 关键路径长度 — cp 值越大越优先
  3. 指令延迟 — 延迟越大的指令越早发射，以隐藏延迟
  4. 原始顺序 — 以上均相同时保持原序

Load-Use Hazard 检测

// candidateHasLoadUseHazard: 检查候选指令是否与前一条有 load-use 冲突
bool MachineScheduler::candidateHasLoadUseHazard(
    MachineInstr *candidate, MachineInstr *lastScheduled) {
    if (!lastScheduled || !lastScheduled->mayLoad)
        return false;
    // 前一条是 load，且 candidate 使用该 load 的定义
    return !candidate->uses.empty() &&
           hasIntersection(lastScheduled->defs, candidate->uses);
}

当检测到 load-use hazard 时，调度器会优先选择其他就绪指令，让 load 结果有更多时间到达寄存器文件，减少流水线气泡。

调度示例

// 调度前：
//   ldr w10, [x29, #-8]    // (1) load a
//   add w11, w10, w3       // (2) a + b  ← load-use hazard!
//   mul w12, w4, w5        // (3) c * d
//   add w13, w12, w6       // (4) result + e

// 调度后（避免 load-use，提前 mul）：
//   ldr w10, [x29, #-8]    // (1) load a
//   mul w12, w4, w5        // (3) c * d  ← 填充 load 延迟
//   add w11, w10, w3       // (2) a + b  ← load 结果已就绪
//   add w13, w12, w6       // (4) result + e
